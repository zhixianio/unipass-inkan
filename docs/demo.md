# 演示脚本：正常转账 + 三个攻击场景

> 状态：2026-10-27（桌面端改成钱包式界面之后）。配合方案文章录屏用。攻击演示只在桌面端的 **DEBUG 构建**里有（`#if DEBUG` 编译期隔离，Release 二进制里没有这段代码，`apps/coordinator/scripts/check-release-no-attack-demo.sh` 核对）。

要演示的是一句话：**桌面端被篡改了也没关系，签名器自己解码、按规则判定，篡改过的请求会被它判红或直接拒签。**

桌面端的发送流程和主流钱包一样（选资产 → 收款人 → 金额 → 核对 → 签名），界面上只有代币单位、名字和一句话摘要；to、data、nonce、交易指纹这些只在核对页折叠的「技术细节」里。攻击演示开着的时候，桌面端**看起来和正常时一模一样**——摘要句、收款人、指纹都是你填的那笔——这正是被篡改的桌面端骗人的方式。

## 准备

| 设备 | 要求 |
|---|---|
| iPhone：UniPass Inkan 签名器 | 已生成密钥；**全程离线**：在**设置**里打开飞行模式、关掉 Wi-Fi 和蓝牙，不插数据线（不要用控制中心：那里的开关只断开到第二天，之后会自动恢复，见[苹果说明](https://support.apple.com/en-us/102412)）。首页应显示"已离线，可以签名"（Offline: ready to sign）。中途如果变成"已联网，不能签名"，停下来，恢复离线再继续 |
| Mac：UniPass Inkan 桌面端 | **Debug 构建**，带启动参数 `-InkanDemo YES` 运行（命令行：`open "…/UniPass Inkan Desktop.app" --args -InkanDemo YES`；Xcode 里在 Scheme › Run › Arguments 加上）。不带这个参数时，主窗口和菜单栏里没有任何演示的痕迹。已和签名器配对 |
| Safe | Sepolia 测试 Safe `0x8ceb…E4a1`（2-of-2：签名器 + 测试 EOA），里面约有 0.009 Sepolia ETH。演示金额用 `0.001`。在侧边栏顶部的 Safe 卡片里选中它；列表里没有的话用「添加已有 Safe」加进来 |
| 提交账户 | 「设置 › 提交账户」：桌面端自己的小钱包，付执行时的网络费，不是 Safe 的 owner。第一次打开时生成。里面要有一点 Sepolia ETH（现在约 0.005），余额低时页面会提示充值 |
| 录签名器 | 用 iPhone **自带的屏幕录制**（控制中心里的录屏按钮只录屏，不会打开网络）。从场景 0 开始一直录到最后一个攻击场景，中间不停，后期再切。录完再插线，用 Mac 的「图像捕捉」或「照片」导入。签名时手机离线就够了：签名器没有网络代码，密钥在安全芯片里导不出来，录完插线导出和每次装新版时联网打开一次是同一回事。**不要**用数据线投屏（QuickTime）录：插着线时签名器判定为联网，会拒签 |
| 录桌面端 | 录主窗口（`screencapture -v` 或 ⇧⌘5），同样从头录到尾。讲解窗口是单独的窗口，放到录制范围之外或另一块屏幕上。签名面板里的相机预览会拍到摄像头前的东西，后期打码 |
| 合成 | 两段录像按画面里的事件对齐（桌面端出现签名二维码 ↔ 签名器开始扫码），并排拼成一段视频，再剪一段短 GIF 放进 README。截图直接从视频里取 |

签名器上地址的前 8 位和后 8 位加粗；桌面端完整地址也是这样显示。交易指纹只是显示，不要求两边比对。

**想演示 USDC？** 测试 Safe 里现在只有 ETH。Circle 的测试网水龙头要人工过验证码：打开 <https://faucet.circle.com>，网络选 **Ethereum Sepolia**，地址填 Safe 的地址（桌面端首页「接收」可以复制），领到后首页「资产」里会出现 USDC（6 位小数），发送流程里就能选它。

## 场景 0：正常转账，从签名到上链

先做这一笔正常的。收款人 Alice 已经在桌面端和签名器的地址簿里了；场景 2（地址投毒）要用到签名器地址簿里的 Alice。

1. **桌面端**：确认讲解窗口（「窗口 › Attack Demo Presenter」，⌃⌥⌘D）里的场景是「关闭」（没打开过讲解窗口时就是关闭）。首页「资产」点「发送」（或 ⌘N）：
   - 选资产：ETH
   - 收款人：在地址簿里点 Alice（`0x938313A5…869AB39a`，测试 EOA，当作"我的另一个钱包"）
   - 金额：`0.001`（可以先填 `1` 演示"Safe 里的 ETH 不够"）
   - 核对页：一句话"发送 0.001 ETH 给 Alice"，收款人全地址首尾 8 位加粗，网络、需要 2 个签名、预计网络费（Sepolia 上不到 0.000001 ETH）；展开「技术细节」能看到 to、data、nonce 和交易指纹
   - 点「让签名器签名」：签名面板出现动态二维码，摄像头自动打开，步骤条在「签名器签名」
2. **签名器**：首页「扫描二维码」扫 Mac 屏幕。
   - 如果是第一次见到这个 Safe，先出现"首次见到这个 Safe"：核对 owner 和门限（2 / 2，其中一个是本机），确认登记。
   - 进入确认页：转 0.001 ETH 给 Alice，收款人是签名器地址簿里的已知地址（绿色）。如果签名器的地址簿被清过，这里会是黄色"首次出现"：点「加入地址簿」，起名 `Alice`（场景 2 需要）。
   - 「用 Face ID 签名」，签名器显示签名二维码。
3. **桌面端**：把签名器的码对准 Mac 摄像头。步骤条依次走过「收回签名」「提交」（自动核对签名、自动保存到 Safe 的交易服务），停在「已上链」这一步，显示"签名 1 / 2"，iPhone 已签、Alice 等待中。
4. **第二个签名**：测试 Safe 的另一个 owner 是测试 EOA（一次性测试网账户）。在仓库根目录：

   ```bash
   H=<核对页「技术细节」里的「交易指纹（完整）」>
   SIG=$(cast wallet sign --no-hash $H --account <你的测试账户>)   # 按提示输入 keystore 密码
   swift run --package-path apps/coordinator/Packages/CoordinatorNetwork sts-write confirm --hash $H --eoa-sig $SIG
   ```

   桌面端每 5 秒刷新一次，变成"签名已集齐"。
5. **执行**：点「执行」，提交账户发出 `execTransaction` 并付网络费（Safe 里的钱不动）。备选：「其他执行方式」里的「在 Safe{Wallet} 中执行」；Debug 构建带 `-InkanDeveloper YES` 启动时还可以展开「测试网执行（调试）」，先「预检 checkSignatures」，再复制 `cast send` 命令用测试 EOA 执行。
6. **核对**：签名面板变成"完成，交易已上链"，有区块浏览器链接；首页余额少 0.001 ETH；「活动」里这一笔是"已上链"。

**截图**：
- 桌面端：首页、选资产、收款人、金额、核对页（展开技术细节）、签名面板（动态二维码 + 步骤条）、活动列表
- 签名器：确认页（转账内容、绿色的已知收款人 Alice）、签名完成页（签名二维码）
- 区块浏览器：执行成功的交易

## 攻击场景通用步骤

1. **桌面端**：从「窗口 › Attack Demo Presenter」（⌃⌥⌘D）打开讲解窗口（这是演示唯一的入口，只在 `-InkanDemo YES` 时出现；不用 ⌥⌘D，那是 macOS 的程序坞快捷键），放到录屏范围之外或另一块屏幕上。在窗口顶部选一个场景（Bybit 式 / 地址投毒 / 退款抽干）。主窗口里什么都不会变。
2. 讲解窗口里有场景说明、预期结果，以及最近一次实际发给签名器的请求（界面显示的指纹 vs 发给签名器的指纹、to、operation、gas 参数）。
3. 主窗口照常走一遍场景 0 的发送：ETH → 地址簿里点 Alice → `0.001` → 核对页。核对页、签名面板和正常时**完全一样**：摘要"发送 0.001 ETH 给 Alice"、Alice 的完整地址、技术细节里的指纹都是你填的那笔。
4. **签名器**扫码，看判定。**不要越过红色、不要签名**。就算越过签了，攻击演示模式下桌面端也不会把签名存进交易服务（签名面板停在「提交」，显示"演示：签名没有保存"）。
5. 演示完在讲解窗口里把场景切回「关闭」，或者不带 `-InkanDemo YES` 重新启动。

| 场景 | 实际发给签名器的 | 签名器预期 |
|---|---|---|
| **Bybit 式** | `to = 0x96221423…105C7242`（Bybit 事件里被 DELEGATECALL 的合约），**operation = DELEGATECALL**，data = `transfer(0xbDd077f6…69516, 0)`，看起来像"转 0 个代币" | **直接拒签**（`delegateCallNotAllowed`），没有越过的入口。拒签原因写明 DELEGATECALL 到 0x96221423…105C7242：这个 Safe 会以自己的身份运行它的代码，可以借此接管 Safe |
| **地址投毒** | 收款人换成 `0x938313` + 中间 28 位全不同 + `9ab39a`，首尾各 6 位和地址簿里的 Alice 相同 | **判红，命中 R05**。两个地址并排显示，不同的字符标红；收款人那里不再加粗首尾（首尾正是伪造的部分）。越过要输入从第一处不同开始的 4 个字符 |
| **退款抽干** | 转账本身不变；`gasPrice = 1000 gwei`、`baseGas = 1,000,000`、`refundReceiver = 0xbDd077f6…69516`，执行时 Safe 要额外"退款"约 1 ETH 给攻击者 | **直接拒签**（`gasRefundNotSupported`），没有越过的入口；"拒签原因"列出 gasPrice、baseGas、gasToken、refundReceiver 四个值 |

**每个场景的截图**：
- 桌面端：核对页和签名面板（和正常时一样）；讲解窗口里"发给签名器的指纹"和界面显示的不同
- 签名器：判定页
  - Bybit 式：拒签页和 DELEGATECALL 的拒签原因
  - 地址投毒：两个地址并排、不同字符标红的那一段
  - 退款抽干：拒签页和"拒签原因"
- 对比镜头（可选）：同一画面里桌面端显示的交易指纹和签名器上的交易指纹不同

## 和自动测试的对应

`apps/coordinator/Packages/CoordinatorKit/Tests/CoordinatorFlowTests/AttackDemoTests.swift` 用和签名器一样的路径（二维码往返 → 解出 `unipass-sign-request` → core 的 `RiskEngine`，"我的 Safe"里有测试 Safe、地址簿里有收款人）核对上表的预期：Bybit 式拒签，原因是 `delegateCallNotAllowed`；地址投毒判红、R05 的 subject 是（伪造地址，地址簿里的真地址）；退款抽干的拒签原因正好是这四个值；不篡改的同一笔转账是绿色。

只在 DEBUG 构建里：

```bash
swift test --package-path apps/coordinator/Packages/CoordinatorKit --filter AttackDemoTests
```

Release 构建里没有攻击演示的代码和文字：

```bash
apps/coordinator/scripts/check-release-no-attack-demo.sh
```
